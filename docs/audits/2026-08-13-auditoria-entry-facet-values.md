# Audit of `cms_entry_facet_values`

## 1. Objective

Verify the materialized projection used by public listings to filter and order
fields stored inside `block_data`, and confirm how it is created and populated
on a server.

## 2. Environment

- Repository: `teatromuseo-cms-domain`.
- Branch: `dev`.
- Date: 2026-08-13.
- Initial state: clean working tree, aligned with `origin/dev`.

## 3. Process Log

### 2026-08-13 — Identification

- Found migration `2026-08-12-100001_CreateCmsEntryFacetValues`.
- Found `EntryFacetValueSynchronizer`, the
  `cms:backfill-entry-facet-values` command, and the write hooks.
- Pending at this point: run quality gates and check local database behavior
  without modifying data.

## 4. Findings

- The migration is DDL: it creates the table, indexes, unique key, and foreign
  keys; it does not insert data.
- Initial data is generated by the backfill command, not by a seeder.
- Normal entry-block writes synchronize the projection.
- Seeders write blocks directly and do not invoke the synchronizer themselves;
  any bootstrap or content load requires a subsequent backfill when it creates
  or modifies entries.
- The local development database confirms the expected population: 61,208
  rows, 875 entries, and 80 field keys. The migration was applied in batch 43;
  the rows were created immediately afterward.
- The current dry-run detects 8,480 entry-owned block translations and is
  idempotent by design.

## 5. Corrections Applied

None. This audit is a review; application code was not changed.

## 9. Final Summary

The implementation is integrated and validated. The migration creates only the
schema; existing content is materialized by
`php spark cms:backfill-entry-facet-values --confirm`, while later edits made
through the normal CMS services synchronize automatically.
